# Остановка Реестра 17 октября 2026 и внешний мониторинг

Задача: https://github.com/nvrtsky/reestr-docs-termech/issues/31. Пользователь уточнил, что клиент проверял на выходных 17–18 октября. Проверку из сети клиента сейчас повторить нельзя.

## Что подтверждено (AC-1)

Журнал VPS Реестра, время Europe/Moscow:

- 17 октября 05:21:44: systemd-logind сообщает `System is powering down (hypervisor initiated shutdown).`
- Последняя запись предыдущей загрузки: 05:22:02.
- Следующая загрузка: 09:56:15, контейнеры приложения запущены около 09:56:27.

Хост был выключен приблизительно 4 часа 34 минуты. Действие инициировано гипервизором; причина решения на стороне платформы хостинга из журналов гостевой ОС неизвестна. Нет оснований связывать выключение с обновлением приложения, нехваткой памяти, оплатой или конкретным оператором.

В доступных kernel/nginx-журналах за 17–18 октября не обнаружено OOM или ошибок upstream приложения. Доступные sysstat-замеры не показывают насыщения CPU; за период выключения замеров нет. Это не исключает кратковременные сетевые проблемы между измерениями.

Точное время попытки клиента неизвестно: подтверждённый простой хоста нельзя выдавать за доказанную причину именно его скриншота. Текущая доступность HTTP 200 также не доказывает отсутствие других прежних проблем.

Повторная проверка доказательств на VPS: `journalctl --list-boots`, `journalctl -b -1 -u systemd-logind -o short-iso`. После следующих перезагрузок выбирать boot по ID из evidence JSON, а не по относительному -1.

## Что установлено (AC-2, AC-3)

На отдельном сервере КП `200.169.189.86` установлен `deploy/monitoring/registry-watch.py`, запускаемый `termech-registry-watch.timer` каждую минуту. Проверяет публичную страницу и `/api/v1/health/ready` на `https://reestr.navrotsky.ru`, а не локальный интерфейс VPS.

Запросы выполняются параллельно, таймаут 8 секунд на запрос, общий лимит systemd 30 секунд. Страница должна вернуть HTML и 200, readiness — JSON со статусом `ready`. Первая/вторая ошибка дают `degraded`, третья подряд — `down`; успешный запрос фиксирует время восстановления и количество неудачных замеров. В записях время UTC. Это проверка доступности, не полного пользовательского сценария и прав сотрудника.

`/var/lib/termech-registry-watch/status.json` содержит текущий результат; `samples.jsonl` и три ротируемых файла сохраняют историю с суммарным пределом около 4 МиБ. Записи также идут в системный journald. Содержимое ответов, OAuth, query-токены и адреса клиентов не сохраняются.

Служба работает с DynamicUser, StateDirectory, ProtectSystem=strict и NoNewPrivileges. Она не перезапускает приложение, не меняет CRM/DNS и не отправляет сообщения. Проверки не предотвращают отключение VPS и не заменяют уведомления ответственного администратора.

## Проверка и обслуживание (AC-4)

На сервере КП:

```sh
systemctl status termech-registry-watch.timer
systemctl list-timers termech-registry-watch.timer
cat /var/lib/termech-registry-watch/status.json
journalctl -u termech-registry-watch.service --since today
```

19 октября подтверждены успешные внешние ответы страницы и API, автозапуск таймера и повторные замеры. Штатная установка: скрипт в `/opt/thermech/monitoring/registry-watch.py` (755), unit-файлы в `/etc/systemd/system/` (644), `systemd-analyze verify`, `systemctl daemon-reload`, `systemctl enable --now termech-registry-watch.timer`. Требуется Python 3, сторонних пакетов нет.

Проверки в изолированной worktree:

```sh
python3 -m unittest discover -s deploy/monitoring -p 'test_*.py'
npm run typecheck
npm run build
```

Три теста проверяют три последовательных отказа и восстановление, отсутствие секретного текста исключения в журнале, атомарную запись состояния и ротацию. Все прошли, typecheck/build прошли. UI приложения не менялся, отдельная браузерная приёмка этого изменения не требуется.

Остановка/удаление мониторинга: `systemctl disable --now termech-registry-watch.timer`, затем `systemctl stop termech-registry-watch.service`; удалить только два unit-файла `termech-registry-watch.*` и скрипт `/opt/thermech/monitoring/registry-watch.py`, выполнить `systemctl daemon-reload`. Историю в StateDirectory можно сохранить для разбора. Рабочие контейнеры при этом не затрагиваются.
